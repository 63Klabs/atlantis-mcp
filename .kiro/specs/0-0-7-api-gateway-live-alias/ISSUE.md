# API Gateway invokes the Read function's $LATEST instead of the live alias

Raised as finding 4 in the [post-deploy smoke verification plan](../0-0-7-postdeploy-smoke-verification/PLAN.md#8-findings-outside-this-spec). Checked against `dev` at `7acaf7d` on 2026-10-21 in the templates, with the SAM translator run locally, and on the deployed `test`, `beta`, and `prod` stacks ([Deployed state](#deployed-state)).

## Summary

In PROD stages (`beta` and `prod`), the Read function is meant to deploy gradually: CodeDeploy moves its `live` alias to the new version 10% at a time, and rolls back when `ReadLambdaErrorsAlarm` fires. API Gateway does not call that alias. The `/mcp/v1` integration targets the function's unqualified ARN, which runs `$LATEST`, so all API traffic switches to the new code as soon as CloudFormation updates the function, before the shift begins. The gradual shift then moves an alias that serves no API traffic. All three deployed stages confirm it: in the last 14 days, the `live` alias served no invocations.

## How it happens

1. **The integration targets the function.** [`template-openapi-spec.yml`](../../../application-infrastructure/template-openapi-spec.yml) L52 builds the `/mcp/v1` integration URI from `${ReadLambdaFunction.Arn}`, the unqualified function ARN. Invoking it runs `$LATEST`.
2. **The alias is what deploys gradually.** In [`template.yml`](../../../application-infrastructure/template.yml) L782-L801, `ReadLambdaFunction` has `AutoPublishAlias: live` and a `DeploymentPreference` that is enabled when `IsProduction`. It uses `FunctionGradualDeploymentType` (default `Linear10PercentEvery3Minutes`, L204-L207, all traffic after about 30 minutes) and rolls back on `ReadLambdaErrorsAlarm` (L799). The build rewrites `AutoPublishCodeSha256` on every run ([`buildspec.yml`](../../../application-infrastructure/buildspec.yml) L160-L161), so every deploy publishes a version and moves the alias.
3. **SAM leaves the URI as written.** I ran `aws-sam-translator` 1.115.0 locally on a template that mirrors `WebApi` and `ReadLambdaFunction`: an explicit `AWS::Serverless::Api` with its own definition, and a function with `AutoPublishAlias: live`, a `DeploymentPreference`, and the `McpV1Post` API event. The generated `AWS::ApiGateway::RestApi` kept `${ReadLambdaFunction.Arn}`, both with the definition inline and as an `AWS::Include`. CloudFormation expands `AWS::Include` before the SAM transform, because it evaluates the most deeply nested macros first ([macro evaluation order](https://docs.aws.amazon.com/AWSCloudFormation/latest/UserGuide/template-macros-author.html)).
4. **API Gateway may invoke either target.** Three permissions apply:

   | Permission | Target | Stages |
   |------------|--------|--------|
   | `ReadLambdaPermission` (L1966) | The unqualified function (`$LATEST`) | All |
   | `ReadLambdaPermissionLive` (L1974) | The `live` alias | PROD |
   | Generated by SAM from the `McpV1Post` event (L918-L924) | The `live` alias | All |

   When `AutoPublishAlias` is set, SAM attaches event-source permissions to the alias; the local translation put the event's permission on `ReadLambdaFunctionAliaslive`. Only the first permission serves the integration as written.
5. **The pattern comes from the starter.** Atlantis starter 02 (`atlantis-starter-02-apigw-lambda-cache-data-nodejs` v0.0.47) also builds its OpenAPI integration from `${WebService.Arn}`, while its `ConfigWebServiceLambdaPermissionLive` carries the comment "Only needed in production for gradual deployments". The workspace steering file [`openapi-spec-sync.md`](../../steering/openapi-spec-sync.md) prescribes `${ReadLambdaFunction.Arn}` in its examples (L61, L111, L118), so new endpoints would repeat it.

## Deployed state

Read-only checks on 2026-10-21. The stacks were last updated on 2026-10-08 (`beta`, `prod`) and 2026-10-09 (`test`).

| Stage | `/mcp/v1` integration target | Endpoint type | `live` alias points to | Invocations in 14 days: function / alias |
|-------|------------------------------|---------------|------------------------|------------------------------------------|
| `test` | Unqualified function (`$LATEST`) | `EDGE` | Newest version (193) | 98 / 0 |
| `beta` | Unqualified function (`$LATEST`) | `EDGE` | Newest version (46) | 1 / 0 |
| `prod` | Unqualified function (`$LATEST`) | `EDGE` | Newest version (44) | 1,938 / 0 |

- The alias moves to the newest version on every deploy, as designed. Nothing invokes it.
- For `test` and `prod`, CloudWatch holds `Invocations` only under `FunctionName` and under `Resource` set to the unqualified function name. No metric exists for the alias resource in the last two weeks.
- The function policies match the permission table above. `test` has `ReadLambdaPermission` and SAM's event permission on the alias, scoped to `POST /mcp/v1`. `beta` and `prod` also have `ReadLambdaPermissionLive`.
- No `Errors` were recorded on any stage in the same 14 days, so the rollback path has not been exercised.

## What a PROD deploy does today

The deployed state confirms step 1. Steps 2 and 3 are my reading of the template; no deploy was observed.

1. CloudFormation updates `ReadLambdaFunction`. From then on, every API request runs the new code.
2. CloudFormation publishes a version and updates the `live` alias. CodeDeploy shifts the alias over about 30 minutes, which limits nothing for API callers.
3. `ReadLambdaErrorsAlarm` still sees the API's errors. It watches `AWS/Lambda` `Errors` with only the `FunctionName` dimension (L2115-L2131), which aggregates all versions and aliases, `$LATEST` included ([Lambda metric dimensions](https://docs.aws.amazon.com/lambda/latest/dg/monitoring-metrics-view.html)). If it fires during the shift, CodeDeploy stops, the alias update fails, and CloudFormation rolls the stack back, which should also put the previous code back on `$LATEST`.

So a rollback probably still reaches API callers, but all of them run the new code from step 1 until the rollback finishes, instead of 10% at first. This corrects PLAN finding 4, which said a rollback would not restore the old code for API callers.

## Who is affected

- `beta` and `prod`. `test` deploys all at once by design, so it behaves the same either way.
- Documentation that promises gradual deploys for PROD stages: [`ARCHITECTURE.md`](../../../ARCHITECTURE.md) L824, [`docs/admin-ops/deployment/README.md`](../../../docs/admin-ops/deployment/README.md) L65-L67, and [`docs/admin-ops/deployment/cloudformation-parameters.md`](../../../docs/admin-ops/deployment/cloudformation-parameters.md) L86-L88.
- Not the Auth function. It has no alias and no gradual deployment, so its integrations on `${AuthLambdaFunction.Arn}` are consistent.

## How to re-check

Read-only. Run with the stage's credentials and region, before and after the fix.

```bash
# Find the /mcp/v1 resource, then print its POST integration URI
api_id="<REST_API_ID>"
resource_id=$(aws apigateway get-resources --rest-api-id "$api_id" \
  --query "items[?path=='/mcp/v1'].id" --output text)
aws apigateway get-integration --rest-api-id "$api_id" --resource-id "$resource_id" \
  --http-method POST --query uri --output text
```

A URI ending in `:function:<name>/invocations` targets `$LATEST`; one ending in `:function:<name>:live/invocations` targets the alias.

CloudWatch shows the same thing. Today, `AWS/Lambda` `Invocations` with the `Resource` dimension `<function-name>:live` is zero while the `FunctionName` metric carries the traffic. After the fix, the alias metric should carry it.

## Expected behavior

In PROD stages, API traffic follows the `live` alias: a new version reaches about 10% of requests first, and a rollback returns API callers to the previous version as soon as CodeDeploy moves the alias back. `test` keeps deploying all at once.

## Possible fix

1. **Build the URI from the alias:** `...functions/${ReadLambdaFunction.Alias}/invocations`. The local translator turned that into `${ReadLambdaFunctionAliaslive}`, a reference to the alias ARN. Because `AWS::Include` is expanded before SAM runs, it should work in `template-openapi-spec.yml` too; a `test` deploy confirms it.
2. **Permissions.** SAM's event permission already covers the alias in every stage, so `ReadLambdaPermissionLive` becomes redundant and `ReadLambdaPermission` unused. Keeping the latter for one release keeps a revert of the URI safe.
3. **Every stage.** One URI for all stages is likely enough: `test` moves its alias all at once, so it behaves as it does today.
4. **Conventions.** Update `openapi-spec-sync.md` so new endpoints use the alias, and check whether the starter 02 fix belongs upstream. This repository does not change upstream templates.

## Consequences to plan for

- Once API traffic follows the alias, `update_template_timestamp.py` matters to API callers: a deploy that did not publish a new version would leave them on the old code. Today, they get new code whether or not the alias moves.
- During a PROD shift, two versions serve API traffic at once, so a client can see responses from both, for example two different `serverInfo.version` values. Post-deploy verification is not affected, because CloudFormation finishes the shift before the post-deploy stage starts.

## Open points for planning

- Whether to change the URI for every stage or only PROD stages.
- What happens to `ReadLambdaPermission` and `ReadLambdaPermissionLive`.
- Whether to exercise a rollback on a PROD stage after the change, since none has been observed.
